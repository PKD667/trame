# parallel! lowered to explicit SIMD (CPU): prototype and measurements

The prototype's report, written from a hand run on one node (section 1). The lab experiment that re-measures it, with the
claims and figures, is `README.md`; the files are `src/` (items, lane kernels, `plan::classify`, the bench), `tests/`
(exhaustive, props, alloc) and `results/` (the raw TSV of section 1).

Question: can `parallel!` (INTERFACE.md 5.4) be lowered on CPU to explicit SIMD, forced by trame and not
left to LLVM, with the semantics of 5.4 and results bit-identical to the scalar fold, and is it worth
it? Short answer: yes for the map shape with contiguous keys, and for heavy bodies; no for
reduce-by-key with a light body; no for gathers on this CPU. Numbers and provenance below.

The code is hand-written lane versions of five item bodies. Nothing here is generated by trame, and
no library file is changed. `trame` is a path dependency; the scalar reference is
`trame::__rt::parallel`, the function `parallel!` expands to.

The kernels carry `#[target_feature(enable = "avx2")]` and are chosen at run time by
`is_x86_feature_detected!("avx2")`, so `-C target-cpu` does not change them. It changes the scalar
reference and the tails. Both builds are reported; the first is the main one.

Auto-vectorization does not happen, with or without `target-cpu=znver1`: `objdump -C -d` of
`axpy_ref`, `sum32_ref`, `sum64_ref`, `poly_ref` shows 0 `ymm` instructions in either binary; the
loop is `vmulss`/`vaddss` on `slots[key]` one item at a time (the key is data, so LLVM cannot prove
two items touch different slots). So the lowering has to be forced, and this is why.

### 2.1 What the scalar baseline is, and is not

The scalar reduce loop has two modes on this node. `sum32`, 8 uniform keys, 1e4 items: 728 M/s in
`results/bench-x86-64.tsv` and 274 M/s in `results/knee-x86-64.tsv`, from the same binary in two
processes; 272 M/s at 1e5 in all 12 data seeds (`knee`, second block) and at >= 1e5 in the main run.
The only thing that differs between the two runs of 1e4 is the order of allocations before it, so
where the buffers sit in memory. The same source built with `target-cpu=znver1` flips other points.
I did not find the cause; memory disambiguation or 4K aliasing between the item stream and `slots`
is a guess, not a finding. Consequence: a reduce-by-key speedup quoted against the slow mode (2.2 to
2.8x) is not robust. Against the fast mode it is 1.0x. I report both and claim neither. The `reg`
kernel does not have two modes (580 to 780 M/s).

## 3. Design

### 3.1 Where the lowering lives

`parallel.rs` is shared by every backend. The lowering is its inner kernel:
`parallel(key, f, cx, items, slots)` stays the semantics; a generated `LANES` companion of `f` is the
fast path. Dispatch is per call: has AVX2 (cached by std, no allocation), `0 < slots.len() <= i32::MAX`,
else the scalar loop. Pass 1 (every key below `slots.len()`) is vectorized and, on failure, calls the
scalar pass 1 so the abort and its message are the scalar ones, with no item run. Zero allocation is
kept: the kernels use under 1 KiB of stack, and `tests/alloc.rs` counts 0 allocations over every
kernel's first call.

Options evaluated:

(a) `#[trame::item]` generates the lane version. Recommended. The macro sees tokens, not types, so it
    cannot decide representability alone. It can rewrite the body over a lane type, and rustc then
    decides: the scalar body and the lane body come from the same tokens, so they cannot drift apart,
    and a construct with no lane meaning is a type error naming it. The rewrite replaces literals by
    splats, `if c {a} else {b}` by `select(c, a, b)`, comparison operators by mask-returning methods,
    `as` by named conversions, and counted `for` ranges by unrolled loops; `+ - * /` and unary `-` are
    operator impls on the lane types. Field reads become loads at `offset_of!(I, field)`. Nothing here
    was built: section 3.3 says what it needs.
    `std::simd` is not an option on the pinned toolchain: on rustc 1.98.1 `use std::simd::f32x8`
    fails with E0658, `portable_simd` unstable (issue 86656), tested on the node. The driver's
    nightly (`driver/rust-toolchain.toml`, nightly-2026-04-21) builds checked programs, but the
    library and the dev environment are stable. Use `core::arch` (stable) behind a `Lane` trait, which
    also gives control of the instruction sequence the exactness argument needs. Other ISAs: one
    `Lane` impl per ISA; only x86-64 AVX2 was done.
(b) Structure-of-arrays transposition of the slots. Not needed and costly: `slots` is the user's
    array and has the user's layout; transposing it into an SoA buffer needs a buffer (no allocation
    allowed) or a per-chunk copy in and out, which costs O(slots) per call whatever the items are.
    The register kernel is the one place SoA wins, and there the registers are the SoA buffer:
    <= 64 f32 slots fit in 8 registers.
(c) Map versus reduce. The two are not separate cases: the window kernel classifies each window of
    W consecutive items at run time as contiguous keys (one vector load and store of the slots),
    pairwise distinct (gather, then W scalar stores; AVX2 has no scatter), or conflicting (the W
    items run through the scalar item). Windows run in input order and nothing is reordered, so the
    result, and the state at an abort, are those of the scalar fold. No allocation, no sorting. What
    it cannot do is help a reduction with few keys (conflict rate above): lanes need W distinct keys at
    once, and reordering to get them needs a counting sort of the items by key (a buffer of
    `items.len()` indices, or chunked ranks: a per-key counter table and a second pass, which is as much
    work as the scalar item for a 1-flop body). I did not build that; for bodies of many flops it would
    probably pay, for the measured light bodies it cannot.
    Skewed keys: the window kernel degrades to scalar (above), the register kernel does not care about
    skew (it ignores key distribution) but its cost grows with `ceil(n/8)` registers per item.
    Register kernel exactness: an item adds its value to its own lane and `-0.0` to the others (`x + -0.0
    == x` for every x that is not a signalling NaN; adding `+0.0` would turn a `-0.0` slot into `+0.0`),
    and it keeps one accumulator per key, so each key's additions stay in input order; splitting a key's
    items over two partial sums would reassociate and is not allowed for floats.

### 3.2 Which item bodies are representable

Lane semantics are the scalar semantics, operation by operation. Representable (accepted), with the
lane operation:

| scalar | lane | why it is exact |
|---|---|---|
| f32/f64 `+ - * /`, unary `-`, `abs`, `copysign` | `add/sub/mul/div`, xor sign, and-not sign | IEEE 754 round to nearest even in both; the MXCSR is the same register for SSE scalar and AVX, so denormal handling is the same (INTERFACE.md: no flush to zero) |
| `a * b + c` | `mul` then `add` | Rust does not contract; INTERFACE.md forbids FMA contraction. `mul_add` is refused unless the lane op is a true fma (same result as the scalar one), and then only with the `fma` feature; not built |
| comparisons `< <= > >= == !=` on floats | `cmp_ps` with `_CMP_*_OQ` / `_UQ` chosen to match NaN behaviour (`!=` is unordered-true) | a mask, one per lane |
| `if c { a } else { b }`, `a`/`b` pure expressions | `blendv(b, a, mask)` | both sides are computed; legal only if computing the untaken side cannot abort (see refused) |
| integer `+ - *` that abort on overflow | add plus a sticky fault mask (`x + y` unsigned: `r < x`; signed: sign test) | a fault sends the window to the scalar item, which aborts with the scalar message; tested (u64) |
| `as` between numeric types | exact conversions only: int widening, `f32 as f64`, int to float with the same rounding; `f32 as i32` with the saturating fix (`cvttps` returns `0x80000000` for NaN and out of range; Rust saturates, NaN is 0) | needs the fix-up select; not built |
| `for i in 0..CONST`, array fields with constant index | unrolled; broadcast | the driver already requires counted loops in items |
| `trame::math::f32::*`, `f64::*` | the same portable code over lane types | INTERFACE.md defines them as portable IEEE code with no backend-specific version, so the lane copy is the same arithmetic; `math::f32::exp` uses `as i32` and `from_bits`, so it needs the cast fix-up. Not built |
| reads of `item.field` (numeric fields), `cx.field`, `slot` scalar or numeric struct | load at `offset_of!`, broadcast, gather | see unsafe |

Refused (the item stays scalar; no lowering):

* `f32::min`/`max` (INTERFACE.md: the sign of a zero result is unspecified) and every function outside
  the spec's list that is not `trame::math`;
* a branch whose untaken side can abort (checked arithmetic, indexing, division by an item-dependent
  value) unless the fault mask is masked by the select mask: allowed in principle, not built;
* indexing by an item-dependent value (`cx.table[x.i]`): a gather from `cx`; refused in v1;
* integer division, `%`, shifts by item-dependent amounts, `u64`/`i64` multiply, 128-bit integers
  (AVX2 has no instruction; emulation is possible but not the same cost model);
* slot or item fields that are not numeric (`Option`, enums, references, arrays with item-dependent
  index, `bool` unless widened), items with padding bytes (a vector load of padding reads uninitialised
  bytes; per-field loads instead, or require a plain-data item);
* data-dependent loop bounds (already refused by the driver: items have counted loops only), early
  return, `?`, calls to non-representable functions (transitive), anything with effects (already refused).

Not a refusal of the program: unrepresentable items run through the scalar loop, which is always
correct. Refusal is only reported where lowering was requested.

How the refusal is reported. A lowered item is opt-in: `#[trame::item(key = e, lanes)]`. (That
is a public attribute change; the task forbade changing the surface, so it is a proposal.) With `lanes`,
the macro rewrites the body; a construct it cannot rewrite is a macro error at the construct's span
(`lanes: "f32::max" has no lane form: INTERFACE.md 5.1 leaves the sign of a zero result unspecified`);
a type that has no lane form (a field of `Option<_>`) is a rustc error from the lane trait bound.
The driver already reads item MIR; it should additionally check that the lowered item reaches no
call outside the lane list, which closes the gap that a macro cannot see through a helper function
(`f(..)` called from the body). Without `lanes` nothing changes. This is the opposite of the NVIDIA
case (`backends/nv`), where an unrepresentable plan has no fallback and must be refused before launch;
on CPU the scalar loop is the fallback, so refusal costs speed, not meaning.

### 3.3 The unsafe it needs, and what justifies each

Trame's own code is trusted by the driver, but trusted is not checked. Each unsafe operation and the
check that makes it sound:

1. Calling `#[target_feature(enable="avx2")]` functions: UB on a CPU without AVX2. Guard: the single
   dispatcher calls `is_x86_feature_detected!("avx2")` first. Check: `usable()` in `simd.rs` is the
   only caller of the kernels; a test would be a kernel that is not reachable without it (not built).
2. Loading `W` items by raw pointer: in bounds when `i + W <= items.len()`. Guard: the loop condition.
3. Raw access to slots (`sp.add(key)`, vector load/store at `sp.add(k0)`, gather): in bounds when every
   key `< slots.len()`. Guard: pass 1, which is INTERFACE.md 5.4's own check and runs before any item or
   store. A contiguous window's last slot is `k0 + W - 1`, and all W keys are below `n`, so it is in
   bounds too. Gather indices are signed 32-bit: `n <= i32::MAX` is a dispatch condition.
4. Aliasing: `items: &[I]` and `slots: &mut [S]` cannot overlap (Rust's rule), and within a window the
   gather/scatter lanes have pairwise distinct keys (`distinct8`), so no two lanes touch one slot.
   `distinct8` is checked against the specification on all 3 x 8^8 key tuples (section 4).
5. Item bytes read as vectors: only for item types without padding and with numeric fields (a `Pod`
   bound as trame already uses for messages; `bytemuck` is a dependency). Otherwise per-field loads.
   In this prototype `Xi` and `Kv64` are `repr(C)` with no padding (an explicit `_p` field).
6. Floating point state: the lane code assumes the same MXCSR as scalar code. Both read the same
   register, so FTZ/DAZ set by the host program changes both identically. Not tested with them set.

### 3.4 Exactness argument (and where it stops)

Lemma (schedule). Let `F` be an item function, `x_1..x_m` items with keys `kappa(x_i) < |S|`. Let a
schedule be a sequence of steps; each step applies `F` to a set of items with pairwise distinct keys,
all at once; every item is applied exactly once; and for each key, its items are applied in input
order. Then the final slots equal `seq`'s. Proof sketch: `F(x, s, cx)` reads and writes only `s = S[kappa(x)]`
(and reads `x`, `cx`, which are immutable), so applications to different keys commute, and
within a step all applications are to different keys, so "all at once" equals any order of them.
Project the schedule on one key: it is that key's items in input order, which is `seq`'s fold for
that key. Keys are independent, so the slots are equal. Window kernel: steps are consecutive
windows, and a conflicting window is W steps of one item, so every key sees input order. Register
kernel: one step per item. Both are instances.

What the lemma does not cover, and what covers it instead:
* that each lane operation computes the scalar operation (exact for IEEE add, mul, compare by the
  instruction definitions; checked here by 6000-case property tests on specials, not proved);
* NaN: INTERFACE.md says results are bit-identical except the sign and payload of NaNs, which Rust
  leaves unspecified. The tests use that clause (`same()`), and count where the strict clause would
  fail: 0 (poly) to 2383 (sum32) slots over 6000 cases per kernel. Every one is NaN against NaN. I
  did not isolate the cause; a likely one is two NaNs of different payload meeting in an add, where x86
  returns the first operand and the compiler may emit either operand order, in the scalar loop as much
  as in the lane;
* the abort path: tested, section 4. The window kernel leaves the slots as the scalar fold does at
  the abort (windows run in order, a faulting window is replayed item by item); the register
  kernel never wrote the slots, and replays the whole scalar fold;
* memory safety of the raw accesses: argued in 3.3, not machine-checked (no Miri run: Miri does not
  model `vpgather`; no sanitizer on the stable toolchain).

## 4. Checks run

`cargo test --release --offline -- --nocapture --test-threads=1` on the node (3 test binaries; all pass):

* `tests/alloc.rs`: 0 allocations in the first call of every kernel (per-thread counting allocator,
  the control allocation is counted).

* `tests/exhaustive.rs` (60 s). The kernels depend on the keys only through equality, consecutiveness
  and the block/tail split. `classify8` (the vector code) equals `plan::classify` (the specification)
  on 3 x 8^8 = 50,331,648 key tuples over three alphabets, including `u32::MAX`, `2^31` wrap-arounds
  (contiguous 2, distinct 120,958, conflict 50,210,688 tuples; every class reached). The f32 window
  and dispatch kernels equal the scalar fold bit for bit (NaN payload aside) on every 8-item tuple
  over 8 keys with n=8 and over keys 3..11 with n=11 (16,777,216 each), every 12-item tuple over 4
  keys with n=9 (block plus tail, 16,777,216) and every 9-item tuple over 6 keys with n=8
  (10,077,696). u64: all 16,777,216 8-item tuples over 8 keys (window and register dispatch); and
  1,594,323 overflow cases (6 items over 3 keys, values and slots in {0, 1, MAX}, three slot
  initialisations), 1,442,639 of which abort: the abort/no-abort outcome and the slots after it agree.
* `tests/props.rs` (0.1 s), seeds `0..6000` of a splitmix64 generator (`tests/common`), no external
  crate (proptest, rand and quickcheck are not in the node's offline cache). Key shapes: identity,
  permutation, uniform, skew, runs, shuffled blocks, two hot keys. Values include +-0, denormals, inf,
  NaN with random payload, near-overflow floats. Kernels: axpy, axpy_sel, poly, sum32 window,
  sum32 register/window dispatch (n up to 300): all equal up to NaN payload. u64: 12000 cases, 3700
  overflow aborts with equal message and equal slots. Bad keys: 2000 f32 and 500 u64 cases, same
  message as the scalar abort, no slot written. A failure prints its seed.
